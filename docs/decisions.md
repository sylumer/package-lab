# Decisions

Choices made while carrying out [plan.md](plan.md) where the plan left them open. One line each: date, work package,
the choice, and why.

- 2026-11-13 · P0.1 · `handlers.launch` stays flat (`{ item, cmi?, ...options }`) · the web and UI callers already send flat fields; `item` and `cmi` are the only non-options.
- 2026-11-13 · P0.1 · `wait` (CLI seconds, default 10) and `auto` (UI auto-stop) are both options · `auto` is the UI's name, `wait` the CLI's; the CLI line uses `auto` as `--wait` when set.
- 2026-11-13 · P0.1 · `profile` and `storage` accept any non-empty string, `browser` only `chromium` · the packages that define their values (P2.1, P1.2, P2.3) narrow or widen the checks.
- 2026-11-13 · P0.1 · The More options area gets its JSON and CLI line from a new `options` handler · the UI is classic scripts and can't import `options.js`; one source of truth.
- 2026-11-13 · P0.1 · `--resume-from` stays a job field, not an option; the run sets `options.resume` true when it resumes · a file path isn't a launch option.
- 2026-11-13 · P0.1 · Depth outside 0–5 now throws instead of clamping · the plan says every field is validated.
- 2026-11-13 · P0.1 · Bad `--wait`, `--depth` or UI `auto` values now fail (exit 2) instead of falling back to a default or clamping · every option is validated in one place.
- 2026-11-13 · P0.1 · `options.resume` becomes true when a run uses `--resume-from` · the saved options then describe what the run did.
- 2026-11-13 · orchestrator · plan-status commit hashes are recorded by the next work package's commit · a commit can't contain its own hash
- 2026-11-13 · P0.2 · `furthest` is the highest step reached, not the end of an unbroken run from the start · a course that skips a step (a script failed but the API still worked) is still best described by how far it got; `firstMissing` says what was skipped.
- 2026-11-13 · P0.2 · `looked` and `found` also count any API call, and `found` needs a lookup that found something or a call · API objects found by paths the probe doesn't see (a host's own API) still show progress.
- 2026-11-13 · P0.2 · `progress` takes `{ milestones, counts }` objects (or bare lists) and breaks a tie on furthest by the number of steps reached · the plan says it compares lists and counts; one call shape for both.
- 2026-11-13 · P0.2 · Script tags on other sites are not required for `scripts` · Package Lab's host never sees them requested through the package.
- 2026-11-13 · P0.2 · Milestones are computed in `main.js` and stored in the saved run, and in `run --json` as `milestones` and `furthest` · one place, readers needn't recompute; the report falls back to computing them for older runs.
- 2026-11-13 · P0.2 · The "Got as far as" finding is put first after sorting, though it is `info` · the plan says top of every package run; `verdict()` still picks the first error or warning.
- 2026-11-13 · P0.2 · `launched` counts any 2xx or 3xx response, and the user guide says so · a redirect still means the launch page was served.
- 2026-11-13 · P0.2 · `milestoneFinding` lives in `milestones.js`, not `rules.js` · it formats the milestone list, so it sits beside it; `rules.js` stays findings from trace evidence, and `main.js` adds it first.
- 2026-11-13 · P0.2 · `progress` throws on missing milestone lists, and says "same furthest step (X), more/fewer steps reached" when only the tie-break differs · avoids "reached X (was X)" and silent bad input.
- 2026-11-13 · P0.3 · The base run is always the first row, named `default`, and (for presets) a variant with the same options as an earlier one is left out · the plan says `standard` is "deduplicated", and a run identical to the default would only repeat it (so `api manifest` and `depth 0` don't appear under the defaults).
- 2026-11-13 · P0.3 · `experiment` with neither `--preset` nor `--variants` uses `standard`; both together fail · a useful default beats an error; two sources would be ambiguous.
- 2026-11-13 · P0.3 · The "gets further" warning needs the furthest step to be later, not just more steps reached · the title says "reached X", which a tie on the furthest step would make false.
- 2026-11-13 · P0.3 · The CLI starts one Electron per variant (the existing `runPackage`), the apps run them in one process · reuses the headless path as the plan says; the apps already hold a long-lived process.
- 2026-11-13 · P0.3 · In the apps, each variant runs for `wait` (set from "Stop after", or 10 s if "I stop it") through `auto` · a table of runs needs each to end by itself.
- 2026-11-13 · P0.3 · The Experiments table lives in the page (not the saved state), and a late-joining web client sees only later events · simplest; the runs themselves are all in the runs list.
- 2026-11-13 · P0.3 · `--variants` accepts a list or `{ variants }`, and `--resume-from` applies to every run, as part of the base · the apps treat resume as a base option, so the CLI matches.
- 2026-11-13 · P0.3 · Variants equal to an earlier one are dropped only for presets; variants from a user's file all run · the user wrote them on purpose (a repeat of the default shows run-to-run noise), and silent dropping would surprise.
- 2026-11-13 · P0.3 · In the apps, a variant whose run ends unrecorded is shown as failed and the experiment carries on (a failed default stops it); a run cut short by Stop is left out of results · a truncated run would make misleading comparisons.
- 2026-11-13 · P1.1 · A bare string in `options.files` is accepted and means `{ content }` · P0.1's `files` was text only, so existing options files keep working; the stored form is always `{ content }` or `{ base64 }`.
- 2026-11-13 · P1.1 · Session overrides live in `pkg.overrides` on the server and `launch` uses them when the caller gives no `files` · the web interface has several clients and the plan says "kept in the session's package state"; an explicit `files` (CLI, experiments' variants) always wins.
- 2026-11-13 · P1.1 · The tree is a sorted list with folder rows and indentation, not collapsible folders · simplest thing that is a tree; the filter flattens it.
- 2026-11-13 · P1.1 · Files over 1 MB are not opened in the editor (replace from a file only) · a textarea with huge text is slow, and the plan only requires editing text files.
- 2026-11-13 · P1.1 · Binary replacement goes through the JSON `override-set` handler as base64 (about 15 MB) on desktop and web · one path for both, no new upload endpoint; the path is checked in the handler either way.
- 2026-11-13 · P1.1 · Saving a file back to exactly its original bytes removes the override · it isn't a change, and it keeps "changed files" honest.
- 2026-11-13 · P1.1 · The boot graph is recomputed for a run with overrides, but the static analysis (manifest, script scan) stays the original's · the plan asks only for the boot graph; re-analysing is a later refinement.
- 2026-11-13 · P1.1 · The "got further" comparison finding is made only in the apps, against the latest earlier run of the same item without overrides, and is not rebuilt when a saved run is reopened · it needs the session's earlier runs; the CLI user compares `furthest` or uses an experiment. The "used N changed files" note is rebuilt from `launch.options.files`.
- 2026-11-13 · P1.1 · `--options-from` takes the saved run's whole `launch.options`; `--options` and flags override it, and `--override` adds to its files · most specific wins.
- 2026-11-13 · P1.1 · `src/textdiff.js` is an LCS table with common start/end trimmed and a size cap · P3.3 doesn't exist; P3.3 can replace it with Myers behind the same two functions.
- 2026-11-13 · P1.1 · Changed files are limited to 50 MB each and 200 MB in all, checked in `normaliseOptions` · keeps memory bounded whichever interface sends them; summaries sent to the UI carry paths and sizes only.
- 2026-11-13 · P1.1 · `cliCommand` writes `--override path=path` for each changed file (a local copy at the same relative path is assumed) and not `--options options.json` for files alone · a copyable line that works once the files are saved, without a placeholder to edit.
- 2026-11-13 · P1.1 · Saving from the editor keeps CRLF line endings if the file used them · the textarea turns them into LF; an unchanged save then equals the original and makes no override.
- 2026-11-13 · P1.1 · The Files view isn't redrawn while the editor has focus · run and state events would otherwise reset the cursor and scroll.
- 2026-11-13 · P1.1 · Reopening a saved run does not rebuild the "compared with the run before" finding · accepted: it needs the session's earlier runs.
- 2026-11-13 · P1.2 · pin accessors are `configurable: true`, not `false` as the plan says · a non-configurable window property makes a top-level `let`/`const` of the same name a SyntaxError that stops the whole script, so the can't-pin case would never be reached and the run would be misleading; configurable lets the `let` shadow it and the "Couldn't pin" finding explain.
- 2026-11-13 · P1.2 · known limit of `configurable: true`: content can redefine or delete a pinned name and silently replace the pin · the probe checks the window's descriptor at `load` and reports `pin-failed` ("the content redefined …") if the pin's accessor is gone; a redefinition that is undone before load, or a dotted-path leaf redefined on its object, isn't seen.
- 2026-11-13 · P1.2 · `bodyFile` must be a relative path inside the options file's folder (absolute paths and `..` are refused); total response bodies are capped at 20 MB; if `Fetch.fulfillRequest` fails the request continues to the server and is marked `answerFailed` (a "Couldn’t answer" warning) · the CLI is still a local-files boundary, and a refused answer must not hang the run.
- 2026-11-13 · P1.2 · the can't-pin (`let`/`const`) check is a column-0 regex over `trace.sources`, not the boot graph's `globals()` · `globals()` is private to `bootpath.js`, works only from files (so not saved runs) and doesn't separate `let` from `var` in its output; the trace has the sources of every script the browser parsed, and the check runs again when a saved run is reopened.
- 2026-11-13 · P1.2 · only `mode: 'force'` is accepted for now · every pin record carries `mode`, so P1.5 adds `'watch'` by widening `PIN_MODES` in `src/pins.js` and the probe; accepting a mode that does nothing would be a trap.
- 2026-11-13 · P1.2 · pins accept only `navigator.userAgent` among `navigator.*`, and no `location.*`; `navigator.userAgent` goes through `Emulation.setUserAgentOverride` on every session and ignores `frames` · the plan names only these; refusing the rest in `normaliseOptions` says so at once instead of silently doing nothing. Pins on the user agent aren't checked for being read.
- 2026-11-13 · P1.2 · pin paths are plain identifiers (`a.b.c`), and `window`, `top`, `parent`, `self`, `globalThis`, `document`, `location`, `API`, `API_1484_11`, `__lab*`, `__proto__`, `constructor` and `prototype` are refused · the probe, the host page or the prototype chain depend on them.
- 2026-11-13 · P1.2 · a `match` is a regex only if it looks like `/…/flags` with flags from `imsu`; anything else is a glob (`*`, `?`) · `/api/player/config` has to be a glob, so "starts and ends with a slash" can't be the rule. A glob is tried against the whole URL, the path with its query, and the path alone, so `/api/player/config` works without the host.
- 2026-11-13 · P1.2 · `Fetch.enable` uses one `*` pattern and `answerFor` does the matching · CDP's patterns are globs only (no regex, no method), and the first matching response wins in list order; requests that don't match are continued at once. Package Lab's own `lab://run/__lab/` files are never answered.
- 2026-11-13 · P1.2 · a response with no `Content-Type` gets `application/json` when its body starts with `{` or `[`, else `text/plain`; `Access-Control-Allow-Origin: *` is added unless given · the common case (a JSON stand-in for another site) then works without headers; a response saying otherwise wins.
- 2026-11-13 · P1.2 · `bodyFile` is read by the CLI only (relative to the `--options` file) and `normaliseOptions` refuses it · the web handlers take the options over HTTP, and a path there would read any file the app can; the saved run then holds the content, so it is reproducible. Bodies are text; a binary body isn't supported yet.
- 2026-11-13 · P1.2 · `--answer` is `pattern=@file` or `pattern=status:body` (the pattern ends at the first `=` that is followed by `@` or three digits and a colon), so `?a=1` can appear in a pattern · matches the two forms in the plan without an escape syntax. `--pin` and `--answer` add to the pins and responses from `--options` or `--options-from`.
- 2026-11-13 · P1.2 · `cliCommand` gives `--pin`/`--answer` only when the flag can say all of it (pins: `frames: 'content'`; responses: no method, no headers), else `--options options.json` · the flags have no syntax for the rest.
- 2026-11-13 · P1.2 · pins and answers live in the UI session (`st.pins`, `st.responses`) and go with every launch, like the other controls; the Answers list is in More options and **Answer this request…** is in the Network tab · the plan puts add/edit/remove for pins in Lookups and More options; answers needed a list somewhere to remove them. They aren't kept across reloads of the web page.
- 2026-11-13 · P1.2 · two extra info findings beyond the plan: "A response matched no request", and an `answeredBy` index on answered requests to support it · a wrong pattern is the usual mistake and would otherwise be silent. "Changed a pinned value" is a warning; "Couldn't pin" is a warning.
- 2026-11-13 · P1.2 · `launchParams` is validated as text with no whitespace or `#` and loses a leading `?`/`&`; it's added after the item's own parameters · it is appended to the launch URL (the saved `launch.url` shows it).
- 2026-11-13 · P1.3 · The recording Proxy lives in its own file, `src/host/shape-probe.js`, injected ahead of `probe.js` only when a response is `@probe` · runs without it are unchanged, and the unit tests can run the very same code in a `vm` context without Electron.
- 2026-11-13 · P1.3 · Later rounds are spelled `@probe <skeleton JSON>`: the network gets the JSON, and the probe wraps the real parsed data, so present values are real (a placeholder `false` really is false) and only missing paths get the Proxy · no new field in a response; the probe needs only the URL patterns, not the skeleton.
- 2026-11-13 · P1.3 · The probe matches by URL only, ignoring a response's method · the spec says to match by URL, and `Response` doesn't know its request's method.
- 2026-11-13 · P1.3 · Types that leave no trace on a Proxy (a `===` comparison, `typeof`, a truthiness test) come from the script text at the read's column (V8 gives the column of the property name), from `trace.sources` · it is the only way to see `cfg.lms.version === '2004'`; a read with no visible use falls back to boolean.
- 2026-11-13 · P1.3 · A missing key named like an array or string method (map, trim, includes…) gets a callable Proxy; other missing keys can't be called · calling them behaves like the empty list or text, without making every field `typeof 'function'`. Ambiguous names (includes, indexOf, slice, concat, at) count as array methods.
- 2026-11-13 · P1.3 · `in` on the Proxy says yes, Object.keys lists nothing, `then` and `toJSON` are never reported · yes keeps the content reading deeper (like the always-truthy Proxy); `then` is read by every promise resolution and `toJSON` by JSON.stringify, so they aren't fields.
- 2026-11-13 · P1.3 · Discovery without `--request` works on every fetch or XHR request of the first run outside the package, all in the same rounds, one pattern per path (host root) or origin and path (another site) · one loop instead of one per request; scripts and images from other sites aren't server data.
- 2026-11-13 · P1.3 · The loop is one function, `discover()` in `shape.js`, given a `run` callback: the CLI's `runPackage` and the apps' `runToEnd` (also used by experiments now) · reuses the experiment run path and experiment rows without a third copy of the loop.
- 2026-11-13 · P1.3 · The stand-in's result is the last round's run; with `complete: false` (round limit) the final skeleton was never run, and the finding says there may be more · no extra run just to confirm.
- 2026-11-13 · P1.3 · Discovery shares the experiment slot (one at a time, `experiment-stop` stops it too) and saves its result to `<userData>/discoveries/` in the apps, `discovery.json` in the CLI's `--out` · "saved results" without a loader: the file is for reading or scripts; the runs themselves are saved runs as usual.
- 2026-11-13 · P1.3 · Arrays in real data are returned as they are, not followed · keeps Array.isArray and iteration real; exploring element shapes is a later refinement.
- 2026-11-13 · P1.4 · `instrument(source, { file, base, module })` takes `base`, the first site id, instead of `scriptId`; ids run on across a package's files (`pkg.sites`) and `trace.sites` is that table · an event then needs only one number, and `trace.sites[id]` finds its site with no per-file lookup.
- 2026-11-13 · P1.4 · The page side is its own file, `src/host/trace-probe.js`, injected ahead of `probe.js` only in traced runs · untraced runs are unchanged (no `__lab*` globals), and the unit tests run the very same code under `node:vm` (as P1.3 did).
- 2026-11-13 · P1.4 · Exits are recorded as `return __labR(site, (x))` and `return __labT(2, site)` rather than a call before `return` · no braces needed for `if (a) return`, and the end is recorded after the returned value is worked out; both return what the original did.
- 2026-11-13 · P1.4 · The operand forms compare inside `__labC`, as the plan writes them · operands are still evaluated once, in order; the only visible difference is an extra `__labC` frame for a `valueOf`, `Symbol.hasInstance` or Proxy trap the comparison calls, which `probe.js` leaves out of its stacks.
- 2026-11-13 · P1.4 · The operand form is used only when nothing but the operator lies between the operands (no parentheses), checked with acorn's tokens; otherwise the test is wrapped whole · replacing the operator token is then safe, and no newline is ever removed.
- 2026-11-13 · P1.4 · Every instrumented `.js` file starts with a prelude defining do-nothing `__labT`, `__labR` and `__labC` if they are missing · a worker (which gets no probe) would otherwise throw a ReferenceError; pages always have the probe, so inline scripts get none.
- 2026-11-13 · P1.4 · `trace.sources` gets the original text, and `restoreTrace` moves frame columns, probe stacks and coverage offsets back to the original files · every reader (findings, P1.3's source hints, comparisons, later P1.5 and P4.1) then sees the package's own files, traced or not. For a page, `trace.sources` is the original inline script, as untraced runs record it.
- 2026-11-13 · P1.4 · ponytail: inline-script coverage offsets are mapped through the page's raw text, so a page with CR line endings inside a script gets them shifted; frame columns are mapped by line and column and aren't affected · rare, and coverage of inline scripts is little used; normalise line endings in `restoreTrace` if it matters.
- 2026-11-13 · P1.4 · The 2 MB limit applies to `.js` files as well as pages, and files that aren't UTF-8 text are not traced · the plan's sentence can be read either way; parsing a huge bundle slows serving, and re-encoding non-UTF-8 text would change its bytes.
- 2026-11-13 · P1.4 · `.mjs` files and `type="module"` scripts are parsed as a module first, everything else as a script first · `<!--` means different things in the two, and the browser knows which it is.
- 2026-11-13 · P1.4 · Events are `[t, 1|2, site]`, `[t, 3, site, result, ...previews]` and `[t, 4, site, result, n]` for "repeated n more times"; for `??` the result is 1 when the left had a value; a `switch` records the value's preview · one shape, with the counted repeats in place.
- 2026-11-13 · P1.4 · Object previews give the constructor's name and up to five own keys, but only the name for arrays, typed arrays, windows and DOM objects; a Proxy's traps run when previewed, except Package Lab's own (`__labIsShape`) · listing keys of a 100,000-item array or a window on every test would be slow; there is no way to see keys without running a Proxy's traps, and P1.3's stand-in would otherwise report a `keys` use.
- 2026-11-13 · P1.4 · The 200,000-event ring is kept on both sides: per frame between flushes, and the recorder keeps the newest 200,000 of the run; `trace.exec` is `[]` in untraced runs · what matters is the end of the run; an empty list keeps popup merging simple.
- 2026-11-13 · P1.4 · Pending events are flushed by a `setTimeout` (taken before the content runs) set only while events wait, at page hide, and by the recorder (`__labFlush` in every frame) when the run stops · no standing timer for P1.6's stall analysis to see, and nothing is lost when a run is stopped.
- 2026-11-13 · P1.4 · The Execution tab gets `execTail` (the last 500 events of all frames in time order, described on the server) and `execEvents`; **Code** shows 30 lines either side; a page's code comes from the package (the `source` handler takes a `path`) · the whole trace is too big for the interfaces; a page's original isn't in `trace.sources`.
- 2026-11-13 · P1.4 · The CLI gets `--trace` only; `run --json` is unchanged · the saved run (`--out`) holds the trace, and `lastEvents` reads it; P1.5's `drill` is the command that prints decisions.
- 2026-11-13 · P1.4 · The `hosted` acceptance checks `window.scorm` as true, not false · `scorm.js` has loaded by the time the config request fails, so `startCourse` sees it (the plan assumed otherwise); making it false would stop the fixture's fallback path that other tests rely on.
- 2026-11-13 · P1.4 · Traced and untraced `hosted` are compared on finding titles, without the milestone note · whether `lesson.js` starts before hosted's own API is set is a race, traced or not (the trace shows it), so milestones and the calls listed vary between any two runs.
- 2026-11-13 · P1.4 · Overhead is the time to the launch page's load event on `good`, median of three runs each, with 50 ms of slack on "under twice" (`--slow`) · the load happens in about 80 ms, where a few ms of noise would decide a bare ratio; the CLI's wall time is dominated by `--wait`.
- 2026-11-13 · P1.4 · `PACKAGE_LAB_FORCE_TRACE=1` is applied in `launchItem`, not in `normaliseOptions`; the forced pass is a child run of the whole suite with `--slow` · the options and `cliCommand` unit checks stay as they are, and every end-to-end check (slow ones too) runs traced.
- 2026-11-13 · P1.5 · `drill()` is one pure function called twice (without, then with the watch run's trace); the first call's `watch` list is the paths to watch · the chain's levels come from the static pass, so the watch run can watch every level's path at once, and one run is enough.
- 2026-11-13 · P1.5 · Dead end: the end is the first event after the last reached milestone followed by more than 2 s of silence (else the last event); "functions within 1 s of the first missing milestone's expected moment" is read as decisions within 1 s of the last reached milestone · a missing milestone has no time of its own; the last one reached is when the next was due.
- 2026-11-13 · P1.5 · Which code ran: an event at a site inside the range, else the innermost V8 block-coverage range around its start; inline scripts of pages by events only (ponytail) · coverage offsets of inline scripts are relative to each script and mapping them back wasn't needed for the acceptance cases.
- 2026-11-13 · P1.5 · Only `if`, `? :`, `&&`, `||` and `??` can be key decisions (not loops or `switch`); an `if` without `else` whose branch exits (return, throw…) has the rest of the block as its other branch · `if (!r.ok) throw …; return r.json()` is the hosted case; loops and switches have no single "other branch".
- 2026-11-13 · P1.5 · The chain starts from the last key decision with an undefined or null operand, or a falsy one whose origin is a named cause; other key decisions are listed under it · hosted's `r.ok` is false, not undefined, and the acceptance wants it explained; later decisions with nothing to explain (`live ? … : ''`) would otherwise start the chain.
- 2026-11-13 · P1.5 · A parameter of a callback (`.then`, `.done`, `.success`, `$.getJSON`, `.onload`, `.onreadystatechange`…), or a value from `JSON.parse`/`.json()`/`responseText`, is taken to be the response to the last fetch or XHR request made from the same file before the decision · no data flow analysis; the request's initiator stack gives the file. A request to a package JSON file is checked for the field; a server's isn't visible, so the step points to Discover (P1.3).
- 2026-11-13 · P1.5 · Locals (parameters and names declared in a function) are never watched; only global paths that `pinPathProblem` accepts are · a pin can only be a window property; `API` and `API_1484_11` are judged against the run's `expose` instead (cause `version`).
- 2026-11-13 · P1.5 · Watch pins have no value and can't be on `navigator.userAgent`; a watched name that didn't exist is a non-enumerable accessor until written (ponytail: `name in window` says yes; a Proxy would avoid it). Intermediate names of dotted paths now share one accessor per object (`hooks` in `probe.js`), and pins are installed longest path first · several watches under one root (`config` and `config.cdn`) used to replace each other's root accessor.
- 2026-11-13 · P1.5 · A script that never loaded is explained by the string literal in the package that names it (matched by its path or file name) and the guard around that literal; the guard of a named function's code is the guard of its first call (one hop) · simpler than the boot graph's resolution and enough for loaders built with `createElement('script')`; `globals()` (now exported) only covers names acorn finds no assignment for (known libraries).
- 2026-11-13 · P1.5 · "Why it stopped" is part of the drill-down's result (CLI output, the Drill-down tab), not added to the run's findings; `error` for causes `request`, `script`, `file` (a JSON file without the field, or invalid) and `version`, else `warn` · the run's findings are recomputed from saved runs, and the drill-down needs a second run.
- 2026-11-13 · P1.5 · `drill --out` is a folder (`01-traced.json`, `02-watched.json`, `drill.json`), like `discover` and `experiment`; the first run is always traced whatever `--trace` says · two runs don't fit `run`'s single `--out` file.
- 2026-11-13 · P1.5 · In the apps, `drill-start { run }` works on a chosen run (traced again first if it wasn't), in the experiment slot, with `drill` events · the tab is about a run, like Execution; one background job at a time as for experiments and discovery.
- 2026-11-14 · P1.6 · Timers go out as one summary per frame (per kind and call site; at most once a second for the first 30, then every 5 s, and on page hide and when the recorder stops), not one report per creation, firing or clear · a polling or timeout-chain page would flood the 5,000-report cap; the last summary of a frame is the state at the end. `stall` reads only the last one.
- 2026-11-14 · P1.6 · The recorder always flushes `__labFlushT` as a run stops (a new function, not `__labFlush`), also for untraced runs · `trace-probe.js` defines `__labFlush` as a non-configurable property, so the timer summary can't share it.
- 2026-11-14 · P1.6 · A message is reported by the realm of the window `postMessage` was called on, and its sender is the stack's first line · `parent.postMessage(…)` runs the parent's own function; the sender's frame isn't available.
